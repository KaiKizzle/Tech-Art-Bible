    Addressables

    How Unity's Addressables load content on demand: why direct references load everything, addresses, labels and groups, loading and releasing with reference counts, duplicated dependencies, catalogs and content builds, why builds break, and addressable scenes.

    Builds on GUIDs and .meta Files and Scene Management. Engine notes cover Unity HDRP and URP, with Unreal comparisons.

    Why direct references are not enough

    When a scene or prefab references an asset directly (a prefab in a list, a material in a field), Unity treats it as a hard dependency: loading the scene loads every asset it references, and everything those reference, before the first frame. That is simple and fast for what a level always needs. It breaks down for content that is only sometimes needed: a shop with 200 items, character skins, seasonal events, localised voice lines.

    The old escape hatches have their own problems. The Resources folder puts everything inside it into the build, whether used or not, and builds an index of all of it at startup. Raw AssetBundles load on demand but leave dependency tracking, loading and unloading to you.

    (the com.unity.addressables package) wraps AssetBundles with three things: an address per asset, a catalog that maps addresses to bundles and their dependencies, and reference-counted loading. Code asks for an address; the system finds the bundle, loads its dependencies, and frees it all when the last user lets go, whether the bundle sits in the build or on a server.

    Addresses, labels and groups

    Tick Addressable at the top of an asset's Inspector and it gets an address (by default its path, which you can shorten) and lands in a group, shown in Window > Asset Management > Addressables > Groups. Labels are tags across groups ("Weapons", "Winter") for loading many assets at once.

    A group decides how its assets are built: where the bundles go (local, in the build, or remote, on a server) and its Bundle Mode. Pack Together makes one bundle per group, Pack Separately one per asset, Pack Together By Label one per label. The choice trades the number of files against how much changes when content changes:

    Group by what is loaded and unloaded together, not by asset type. "Forest level", "UI icons" and "Skin: Knight" are good groups; "All textures" is not, because loading one texture keeps that whole bundle around (releasing).

    Loading by address or by reference

    Every load returns an AsyncOperationHandle immediately and completes later, so loading never blocks a frame. The safest key is an field: you drag the asset onto it in the Inspector, it stores the asset's GUID (GUIDs in tools), and it survives renames and moves:

    using UnityEngine;
using UnityEngine.AddressableAssets;
using UnityEngine.ResourceManagement.AsyncOperations;

public class ShopItemView : MonoBehaviour
{
    public AssetReferenceGameObject itemPrefab;   // drag a prefab here; stores its GUID
    GameObject instance;

    async void OnEnable()
    {
        AsyncOperationHandle<GameObject> handle = itemPrefab.LoadAssetAsync();   // +1 on the prefab and its bundle
        GameObject prefab = await handle.Task;
        if (this == null || !enabled) return;     // disabled while loading
        instance = Instantiate(prefab, transform);
    }

    void OnDisable()
    {
        if (instance) Destroy(instance);
        if (itemPrefab.IsValid()) itemPrefab.ReleaseAsset();   // -1: every load needs one release
    }
}

    String addresses and labels work too, and are useful for data-driven content (an item table that lists addresses). They are also the most common source of InvalidKeyException, because nothing checks a string until it runs:

    // By address (a string key) or by label (all assets tagged "Weapons"):
var one = Addressables.LoadAssetAsync<Material>("Materials/Rust");
var all = Addressables.LoadAssetsAsync<GameObject>("Weapons", w => Debug.Log(w.name));
// ...later, once each:
Addressables.Release(one);
Addressables.Release(all);

    Addressables.InstantiateAsync combines load and instantiate; destroy those instances with Addressables.ReleaseInstance so their count goes down.

    Releasing and reference counts

    Addressables counts. Every load of an asset adds one to its count and to its bundle's count; every Release subtracts one. When a bundle's count reaches zero, Unity unloads the bundle and everything loaded from it. One rule follows: one release per load, no more (the handle becomes invalid and the counts go wrong), no less (the memory never comes back).

    The catch is that a bundle cannot be unloaded in part. A released asset stays in memory as long as anything else from its bundle is still held:

    Unity's documentation describes the opposite effect too, churn: releasing the last asset of a bundle unloads it, and if something asks for an asset from it a moment later, the whole bundle loads again. Both point the same way: put assets that live and die together in the same bundle, and keep unrelated assets apart. Resources.UnloadUnusedAssets frees released assets from partly used bundles, but it is slow, so call it on a loading screen. The Addressables Profiler module in the Unity Profiler shows the counts live.

    Dependencies and duplicates

    An addressable prefab depends on its meshes, materials, textures and shaders. If a dependency is addressable itself, Addressables loads its bundle first. If it is not, the build copies it into every bundle that needs it. Two groups using the same non-addressable texture atlas get two copies, on disk and, when both are loaded, in memory:

    Duplicates are more than wasted megabytes. A duplicated ScriptableObject is two objects with two states; a duplicated material breaks material batching; a shader duplicated across bundles compiles twice. The same happens between Addressables and assets referenced directly by scenes in the build, or placed in a Resources folder.

    Find them with Window > Asset Management > Addressables > Analyze: the rule Check Duplicate Bundle Dependencies lists implicit duplicates and its fix moves them into a new shared group. Read the list before fixing: Unity's documentation warns that the automatic fix can be harmful, for example for an FBX whose meshes are split across groups. The build report (Addressables Report) shows the same information per bundle after each build.

    Catalogs and content builds

    Addressables content is built separately from the player: Build > New Build > Default Build Script in the Groups window writes the bundles and a , the file that maps every address and label to a bundle, its dependencies and its location. At startup the player loads the catalog; every load after that is a catalog lookup. Content is built per platform, like the player.

    • Build with the player. In the Addressable Asset Settings, under Build, set content to build as part of every player build, or a player can ship with an old catalog, or none.
    • Test with real bundles. The Groups window's Play Mode Script defaults to Use Asset Database, which reads assets directly and skips bundles entirely. It is fast and hides every build problem; switch to Use Existing Build before you trust a result.
    • Remote content. Groups with remote paths go to a server. Shipping a change means Update a Previous Build, which uses the content state file saved by the original build to keep unchanged bundles identical; players fetch the new catalog with CheckForCatalogUpdates and UpdateCatalogs.

    Addressable scenes

    Scenes can be addressable too, which moves their content out of the player build and lets them be downloaded later. They load through Addressables instead of SceneManager:

    // Load additively; the handle owns the scene and its dependencies.
var h = Addressables.LoadSceneAsync("Levels/Forest", LoadSceneMode.Additive, activateOnLoad: false);
await h.Task;
await h.Result.ActivateAsync();            // activation, like allowSceneActivation
SceneManager.SetActiveScene(h.Result.Scene);
// ...later:
await Addressables.UnloadSceneAsync(h).Task;  // unloads the scene and releases its bundles

    An addressable scene must not also be in the Build Profiles scene list: it would be built twice and loaded the wrong way. Keep only the bootstrap there (the bootstrap pattern). Unload with Addressables.UnloadSceneAsync and the handle you got from loading; unloading through SceneManager leaves the bundle counts behind. Everything from scene memory still applies: free unused assets behind a loading screen and watch the activation frame.

    Set it up in Unity

    Setup from package to build, plus three files that remove the usual bugs: a scope object that releases everything it loaded, a spawner for addressable prefabs, and an editor guard that fails a build when Addressables content would be missing or a scene is in both systems. Written for Unity 6; Unity 2022 LTS works the same apart from a few renamed menu entries (Build Profiles was Build Settings).

    Engine settingsPackage, groups, labels, Play Mode Script, build settings.
    Runtime scriptAddressableScope.cs: loads, and releases all on Dispose.
    Runtime scriptAddressableSpawner.cs: InstantiateAsync and ReleaseInstance.
    Editor scriptAddressablesBuildGuard.cs: checks before every player build.
    1. Install Addressables from the Package Manager (Unity Registry). Open Window > Asset Management > Addressables > Groups and click Create Addressables Settings.
    2. Create groups by what loads together (for example UI, Level_Forest, Skins_Knight, Shared). Tick Addressable on assets or drag them into groups; shorten addresses (right-click, Simplify Addressable Names) and add labels where you load sets.
    3. For each group, set Bundle Mode: Pack Together for content that loads as a unit, Pack Separately for large, independently loaded items. Put textures, materials and shaders used by several groups into Shared.
    4. Run Analyze (Window > Asset Management > Addressables > Analyze), rule Check Duplicate Bundle Dependencies. Read the list, then fix by moving the shared assets to Shared yourself or with Fix Selected Rules.
    5. In the Addressable Asset Settings, under Build, set Addressables to build with every player build. Put AddressablesBuildGuard.cs in an Editor folder: it fails a player build when that setting is off, and when a scene is both addressable and in the Build Profiles list.
    6. Load in code through AddressableScope: create one per screen or level, await scope.Load<T>(key) as often as needed, and call Dispose() when the screen closes. Every handle it opened is released exactly once, which removes both leaks and double releases.
    7. For spawned objects, put AddressableSpawner on a manager and call Spawn and Despawn. It uses InstantiateAsync and ReleaseInstance, so instance counts stay right.
    8. Before testing a build-related bug, switch the Groups window's Play Mode Script to Use Existing Build and build content once (Build > New Build > Default Build Script). Watch counts in the Profiler's Addressables module.
    using System;
using System.Collections.Generic;
using System.Threading.Tasks;
using UnityEngine.AddressableAssets;
using UnityEngine.ResourceManagement.AsyncOperations;

// Owns every handle it loads and releases them all, once, on Dispose.
// Typical use: one scope per screen or level.
public sealed class AddressableScope : IDisposable
{
    readonly List<AsyncOperationHandle> handles = new List<AsyncOperationHandle>();
    bool disposed;

    public async Task<T> Load<T>(object key)
    {
        if (disposed) throw new ObjectDisposedException(nameof(AddressableScope));
        var h = Addressables.LoadAssetAsync<T>(key);
        handles.Add(h);                         // tracked even if awaiting throws
        return await h.Task;
    }

    public async Task<IList<T>> LoadAll<T>(object label)
    {
        if (disposed) throw new ObjectDisposedException(nameof(AddressableScope));
        var h = Addressables.LoadAssetsAsync<T>(label, null);
        handles.Add(h);
        return await h.Task;
    }

    public void Dispose()
    {
        if (disposed) return;
        disposed = true;
        foreach (var h in handles)
            if (h.IsValid()) Addressables.Release(h);
        handles.Clear();
    }
}
    using System.Collections.Generic;
using System.Threading.Tasks;
using UnityEngine;
using UnityEngine.AddressableAssets;

// Spawns addressable prefabs; each instance holds one reference until Despawn.
public class AddressableSpawner : MonoBehaviour
{
    readonly HashSet<GameObject> live = new HashSet<GameObject>();

    public async Task<GameObject> Spawn(AssetReferenceGameObject prefab, Vector3 pos, Quaternion rot)
    {
        var h = Addressables.InstantiateAsync(prefab, pos, rot);
        GameObject go = await h.Task;
        if (go != null) live.Add(go);
        return go;
    }

    public void Despawn(GameObject go)
    {
        if (go == null || !live.Remove(go)) return;
        Addressables.ReleaseInstance(go);       // destroys it and releases its reference
    }

    void OnDestroy()
    {
        foreach (var go in live) if (go != null) Addressables.ReleaseInstance(go);
        live.Clear();
    }
}
    #if UNITY_EDITOR
using UnityEditor;
using UnityEditor.AddressableAssets;
using UnityEditor.AddressableAssets.Settings;
using UnityEditor.Build;
using UnityEditor.Build.Reporting;
using UnityEngine;

// Fails a player build that would ship without Addressables content, or with a scene in both systems.
public class AddressablesBuildGuard : IPreprocessBuildWithReport
{
    public int callbackOrder => -100;

    public void OnPreprocessBuild(BuildReport report)
    {
        var settings = AddressableAssetSettingsDefaultObject.Settings;
        if (settings == null) return;                                   // project does not use Addressables

        if (settings.BuildAddressablesWithPlayerBuild == AddressableAssetSettings.PlayerBuildOption.DoNotBuildWithPlayer)
            throw new BuildFailedException("Addressables are set not to build with the player. " +
                "Build content first, or enable building with the player in the Addressable Asset Settings.");
        if (settings.BuildAddressablesWithPlayerBuild == AddressableAssetSettings.PlayerBuildOption.PreferencesValue)
            Debug.LogWarning("Addressables build with the player only if your Editor preferences say so. Prefer the explicit project setting.");

        foreach (var s in EditorBuildSettings.scenes)
        {
            if (!s.enabled) continue;
            if (settings.FindAssetEntry(s.guid.ToString()) != null)
                throw new BuildFailedException($"{s.path} is addressable and also in the build scene list. Remove it from one of them.");
        }
    }
}
#endif

    AddressableScope keeps assets alive until it is disposed, which is the point: a level's scope holds the level's content. For assets that should outlive any screen (fonts, shared UI atlases) use a scope owned by the bootstrap scene (bootstrap pattern).

    Addressables are pipeline independent. Shader stripping differs per pipeline: if bundled materials render pink only in builds, check the pipeline asset's stripping settings and keep shaders in a shared group.
    Unreal's equivalents are soft references (TSoftObjectPtr, loaded with the Asset Manager or Async Load Asset in Blueprint) for on-demand loading, and chunking with Primary Asset Labels for packaging content into separate pak files. Hard references load everything, exactly as in Unity.
