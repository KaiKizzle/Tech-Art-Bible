    Rays, Spheres and Shaders

    The first stage of any sky, atmosphere or cloud effect: for every pixel, the direction it looks and where that ray crosses a layer around a curved planet. Every step is a formula you can move.

    Engine notes cover Unity HDRP, Unity URP and Unreal. Test values are given so you can check your own implementation.

    What we are building

    Volumetric clouds are drawn by walking along a line from the camera through the sky and adding up how much cloud each step passes through. Before that walk can start, every pixel needs two answers: in which direction does this pixel look, and between which two distances does that line pass through the cloud layer? This unit builds exactly that first stage, as a full-screen pass.

    The cloud layer is a shell around the planet, from 1500 m to 2500 m above the ground. The planet is curved, so the shell is curved too: looking straight up, a ray crosses 1000 m of it; looking at the horizon, it travels well over a hundred kilometres before it even reaches the layer. The side view below is exaggerated so the curve is visible.

    DiagramOne ray per pixel, cut by the cloud layerChange the camera's view angle; each line is one pixel's ray.

    The thick parts of the rays are inside the layer. The rest of this unit computes their start and end for every pixel.

    The pass is a pixel shader that runs once for every pixel of the screen (one small program per pixel). Its steps are the chapters of this unit:

    1. From the pixel's position to NDC
    2. From NDC to a direction relative to the camera
    3. From that to a direction in the world
    4. Describe the planet and the layer as spheres
    5. Intersect the ray with both spheres, then pick the right distances
    6. Pass the settings in from the CPU and write the result

    From a pixel to UV and NDC

    A full-screen pass draws one big triangle (or quad) over the whole screen, so the pixel shader runs once for every pixel. The only thing it knows at first is which pixel it is: its column and row, given by the SV_Position input. Their values sit at pixel centres: 0.5, 1.5, 2.5 and so on.

    Two small conversions, the same as in From NDC to pixels and back run in reverse, turn that into a resolution-independent position: UV from 0 to 1, then NDC from −1 to +1, which is what the camera maths uses.

    Do the same for the row to get the vertical value. Mind the direction: rows count downwards, NDC y counts upwards, so on most platforms the vertical NDC is 1 − 2·uv.y instead of 2·uv.y − 1. If your sky comes out upside down, this is the line to check.

    From NDC to a direction from the camera

    A camera turns a direction into a screen position by dividing by distance (the perspective divide). For a ray we need the opposite: start from the screen position and build the direction it came from.

    In view space the camera sits at the origin and looks along +z. Take a point one unit in front of it. The top edge of the screen is at height tan(fov/2) at that distance, so a pixel at NDC y sits at height ndc.y · tan(fov/2). The direction from the camera to that point, normalized, is the pixel's view ray:

    The horizontal part is the same with one extra factor, the aspect ratio (width / height), because NDC x runs from −1 to +1 across a wider screen: d = normalize(ndc.x · tan(fov/2) · aspect, ndc.y · tan(fov/2), 1). Engines usually give you the inverse projection matrix, which does this in one multiplication; the formula above is what that matrix contains.

    Turning the ray into the world, camera-relative

    The view-space direction is relative to the camera's orientation. To know where it points in the world, rotate it by the camera's rotation, the camera-to-world matrix used as a direction transform (w = 0). In the side view used throughout this unit, rotation is one angle: the world elevation of the ray is the camera's pitch plus the pixel's angle inside the view.

    Where does the ray start? At the camera. Here a practical detail matters. A float has 24 bits of precision, about seven significant digits. Positions far from the origin lose their small digits: at the size of a planet, the gaps between representable numbers are half a metre:

    The fix is to measure everything from the camera: coordinates. The ray then always starts at (0, 0, 0), small numbers stay near the viewer where precision matters, and the planet's large radius only appears once, as a constant. Unity HDRP renders camera-relative by default; this unit does the same.

    The planet and the layer as spheres

    The ground is a sphere of radius R = 6 371 km (the Earth's mean radius). The camera stands h metres above it. In camera-relative coordinates the camera is at the origin, so the planet's centre is straight below it at C = (0, −(R + h), 0).

    The cloud layer is everything between two larger spheres around the same centre: radius R + 1500 m and R + 2500 m. A point's altitude is its distance from the centre minus R. Follow one ray and watch its altitude grow, faster and faster, because the ground curves away below it:

    For a horizontal ray, the altitude after a distance t is close to h + t² / (2R): over 10 km that adds only 7.8 m, over 100 km already 785 m. Curvature is negligible for nearby objects and decisive for the horizon.

    Where the ray enters and leaves the layer

    Now the ray-sphere formula does the work, once per sphere. With the ray starting at the origin, L = O − C = (0, R + h, 0), so the two numbers of the quadratic become very simple:

    • b = dot(L, D) = (R + h) · Dy, where Dy = sin(elevation);
    • c = dot(L, L) − r² = (R + h)² − r².

    The camera is below both spheres, so it is inside both, and c is negative (which t do you want). Each sphere then has exactly one hit ahead, t1 = −b + √(b² − c): the point where the ray climbs through that altitude. The ray enters the layer where it crosses the lower sphere and leaves where it crosses the upper one.

    Three numbers to remember, because they are the test values for your shader. Straight up (90°): enter at 1498 m, leave at 2498 m, the altitudes minus the 2 m eye height, and a path of exactly 1000 m. Horizontal (0°): enter at about 138 km. If your implementation prints these, the intersection is right.

    When the camera is inside or above the layer

    A flight game or a mountain top puts the camera inside the layer or above it. The same two sphere tests still give all the answers; only the choice of t changes. Use c (inside or outside each sphere) to tell the cases apart:

    • Below the layer: enter at the lower sphere's t1, leave at the upper sphere's t1 (previous chapter).
    • Inside the layer: the march starts right at the camera (enter = 0). It ends where the ray leaves the upper sphere, or earlier if it is looking down and hits the lower sphere first.
    • Above the layer: the ray enters the upper sphere at its t0, if it hits it at all, and leaves at the lower sphere's t0, or at the upper sphere's t1 if it misses the lower one.

    Getting the settings to the shader

    The shader needs a handful of numbers that are the same for every pixel: the planet radius, the layer's bottom and top, the camera height, and the camera's rotation and field of view. These are properties, stored in a constant buffer and set from a script once per frame.

    // HLSL: the values the pass reads
CBUFFER_START(CloudParams)
    float  _PlanetRadius;      // 6371000
    float  _LayerBottom;       // 1500, metres above ground
    float  _LayerTop;          // 2500
    float  _CameraHeight;      // metres above ground, updated every frame
CBUFFER_END             // four floats: exactly one 16-byte row

    Use a Custom Pass Volume with a Full Screen Custom Pass and a material made from a Fullscreen Shader Graph, or a hand-written shader with a FullScreenPass pass. Set the values with material.SetFloat("_CameraHeight", cam.transform.position.y - groundHeight) in a script, or from the Custom Pass. The camera-relative view direction is available from the view-direction helpers, so you rarely build the view ray by hand in HDRP.

    Add a Full Screen Pass Renderer Feature to the URP renderer and give it a material made from a Fullscreen Shader Graph. Set properties on that material from a script each frame. URP is not camera-relative: subtract _WorldSpaceCameraPos yourself to get a camera-relative ray.

    Use a post process material (Material Domain: Post Process) in a Post Process Volume. Unreal is Z-up and uses centimetres, so the planet centre is (0, 0, −(R + h)) and R = 637 100 000. Camera Vector gives the per-pixel world direction; scalar parameters set from a Material Parameter Collection carry the layer settings.

    Writing the result into the frame

    At this stage the pass does not draw clouds yet. To check the maths, output the distance through the layer as a colour and compare with the test values from the hit chapter.

    When the march along the ray is added later, it produces two things: the light the clouds add, and how much of the background still shines through them, the T. Light passing through a uniform medium of density σ over a distance d is reduced exponentially (the Beer–Lambert law). The pass then blends with the frame below: result = clouds + background · T, which the GPU does for you with the blend mode Blend One SrcAlpha and T in the alpha channel (blend modes). The march itself, step by step, is the next unit: Marching a Cloud Layer.

    // The complete first stage. Output: distance through the layer as a debug value.
float4 Frag(float4 pos : SV_Position) : SV_Target
{
    float2 uv  = pos.xy / _ScreenSize.xy;              // SV_Position is already at pixel centres
    float2 ndc = float2(uv.x * 2 - 1, 1 - uv.y * 2);   // y flipped
    float  k   = tan(_FovY * 0.5);
    float3 dV  = normalize(float3(ndc.x * k * _Aspect, ndc.y * k, 1));
    float3 rd  = mul((float3x3)_CameraToWorld, dV);      // rotation only

    float3 C   = float3(0, -(_PlanetRadius + _CameraHeight), 0);
    float2 lo  = RaySphere(0, rd, C, _PlanetRadius + _LayerBottom);
    float2 hi  = RaySphere(0, rd, C, _PlanetRadius + _LayerTop);
    float  tEnter = lo.y, tExit = hi.y;                     // camera below the layer
    float  d   = max(0, tExit - tEnter);
    return float4(d / 20000.0, 0, 0, 0);             // red = distance, alpha 0 = replace
}

    Build it in Unity HDRP

    The full-screen pass of this unit, built the HDRP way: a Fullscreen Shader Graph drawn by a Custom Pass Volume, with the camera settings sent by C# exactly as in getting the settings to the shader. The debug output shows the distance through the cloud layer. Written for Unity 6 with HDRP 17; Unity 2022 LTS works the same apart from a few renamed menu entries.

    Custom PassA Custom Pass Volume with a FullScreen Custom Pass.
    Shader GraphA Fullscreen Shader Graph.
    HLSL fileRayLayer.hlsl: pixel to ray, ray against the layer.
    C# scriptCameraRayParams.cs: camera basis and lens, once per frame.
    1. Add CameraRayParams.cs to the main camera.
    2. Create Create > Shader Graph > HDRP > Fullscreen Shader Graph. In Graph Settings set Blend Mode to Alpha.
    3. Save RayLayer.hlsl. In the graph, add a Custom Function node. Set Type to File, Source to RayLayer.hlsl and Name to RayLayerDebug (without the _float suffix). Add the inputs UV (Vector 2), PlanetRadius (Float), CameraHeight (Float), Bottom (Float), Top (Float) and the outputs Color (Vector 3), Alpha (Float), Distance (Float), in that order and with those types: they must match the function's parameters.
    4. Connect a Screen Position node (Mode Default, .xy) to UV, and Floats for the planet radius (6 371 000), the camera height (or the camera's y from a property), the layer bottom (1500) and top (2500). Connect Color and Alpha to the fragment outputs.
    5. Create a material from the graph. Add an empty GameObject with a Custom Pass Volume (Mode Global, Injection Point Before Post Process), click +, choose FullScreen Custom Pass and assign the material.
    6. The view shows the distance through the layer as a gradient over the sky; geometry in front is left alone because the shader checks the scene depth. Fly the camera into and above the layer to see the three cases.
    #ifndef ATLAS_CAMERA_RAY_DECLARED
#define ATLAS_CAMERA_RAY_DECLARED
float3 _CamRight, _CamUp, _CamForward, _CamPosAWS;
float4 _CamLens;                 // x = tan(fov/2), y = aspect

// Screen UV (0..1, origin bottom-left) to a normalized world-space ray direction.
float3 CameraRay(float2 uv)
{
    float2 ndc = uv * 2.0 - 1.0;
    float3 dView = float3(ndc.x * _CamLens.x * _CamLens.y, ndc.y * _CamLens.x, 1.0);
    return normalize(dView.x * _CamRight + dView.y * _CamUp + dView.z * _CamForward);
}

// Ray from a point at height h above a planet of radius R against the sphere of radius r.
// Planet centre is at (0, -(R + h), 0) in camera-relative space.
float2 RaySphereFromHeight(float3 dir, float R, float h, float r)
{
    float b = (R + h) * dir.y;
    float c = (R + h) * (R + h) - r * r;
    float d = b * b - c;
    if (d < 0) return float2(-1, -1);
    d = sqrt(d);
    return float2(-b - d, -b + d);
}

// Where a ray enters and leaves the layer between R + bottom and R + top (camera below, inside or above).
float2 LayerInterval(float3 dir, float R, float h, float bottom, float top)
{
    float2 lo = RaySphereFromHeight(dir, R, h, R + bottom);
    float2 hi = RaySphereFromHeight(dir, R, h, R + top);
    float t0, t1;
    if (h < bottom)      { t0 = lo.y; t1 = hi.y; }                                   // below the layer
    else if (h < top)    { t0 = 0; t1 = (lo.x > 0) ? lo.x : hi.y; }                  // inside
    else                 { if (hi.x < 0) return float2(-1, -1); t0 = hi.x; t1 = (lo.x > 0) ? lo.x : hi.y; }  // above
    return float2(max(t0, 0), t1);
}
#endif

#ifndef ATLAS_RAY_LAYER_INCLUDED
#define ATLAS_RAY_LAYER_INCLUDED

void RayLayerDebug_float(float2 UV, float PlanetRadius, float CameraHeight, float Bottom, float Top,
                         out float3 Color, out float Alpha, out float Distance)
{
    float3 dir = CameraRay(UV);
    float2 seg = LayerInterval(dir, PlanetRadius, CameraHeight, Bottom, Top);
    Distance = seg.y > seg.x ? seg.y - seg.x : 0.0;

    // skip pixels covered by geometry (HDRP: depth from the camera's depth buffer)
#ifdef SHADERGRAPH_PREVIEW
    float depth = 0;                                          // no depth buffer in the node preview
#else
    float depth = SampleCameraDepth(UV);
#endif
    bool sky = depth <= 0.0 + 1e-7 || depth >= 1.0 - 1e-7;   // reversed Z: the far plane is 0
    float k = saturate(Distance / 20000.0);
    Color = lerp(float3(0.1, 0.2, 0.6), float3(1.0, 0.6, 0.2), k);
    Alpha = (sky && Distance > 0) ? 0.85 : 0.0;
}

    using UnityEngine;

// Sends the camera's basis, field of view and position to all shaders, once per frame.
// Put it on the camera that renders the full-screen pass.
[ExecuteAlways, RequireComponent(typeof(Camera))]
public class CameraRayParams : MonoBehaviour
{
    static readonly int RightId = Shader.PropertyToID("_CamRight");
    static readonly int UpId = Shader.PropertyToID("_CamUp");
    static readonly int FwdId = Shader.PropertyToID("_CamForward");
    static readonly int LensId = Shader.PropertyToID("_CamLens");      // x = tan(fov/2), y = aspect
    static readonly int PosId = Shader.PropertyToID("_CamPosAWS");     // absolute world position

    void LateUpdate()
    {
        var cam = GetComponent<Camera>();
        Transform t = cam.transform;
        Shader.SetGlobalVector(RightId, t.right);
        Shader.SetGlobalVector(UpId, t.up);
        Shader.SetGlobalVector(FwdId, t.forward);
        Shader.SetGlobalVector(LensId, new Vector4(Mathf.Tan(cam.fieldOfView * 0.5f * Mathf.Deg2Rad), cam.aspect, 0, 0));
        Shader.SetGlobalVector(PosId, t.position);
    }
}

    HDRP renders with reversed Z on every modern platform, so the far plane reads as 0 and the near plane as 1; the check above accepts either end so it also works where Z is not reversed. With the interval working, Marching a Cloud Layer replaces the debug colour with real clouds.

    Create a Fullscreen Shader Graph (URP) and add the Full Screen Pass Renderer Feature to the URP Renderer, with the material and an injection point of Before Rendering Post Processing. Replace SampleCameraDepth with SampleSceneDepth from DeclareDepthTexture.hlsl (enable Depth Texture on the URP asset).

    Use a Post Process Material (Material Domain: Post Process, Blendable Location: Before Tonemapping) on a Post Process Volume. The camera ray is -CameraVector in a post-process material, scene depth comes from SceneDepth, and parameters come from a Material Parameter Collection.
