    Texels on a Budget

    Textures are usually the biggest item in a game's memory. Four decisions set their cost: resolution, format, mipmaps, and what goes in which channel. Each comes with its formula, live.

    From bytes per texel down to the bits in a 4×4 block, with notes for Unity HDRP, Unity URP and Unreal.

    What a texture costs

    A texture in GPU memory is a grid of (what a texture is). Its format fixes how many . Multiply, divide by 8 for bytes, and add a third if the texture has a mip chain:

    Two things stand out when you move the sliders. Doubling the resolution quadruples the memory, because both sides double. And the format changes the result by a factor of eight: compression is not a polish step, it is the main lever.

    The file on disk tells you nothing. A 6 MB PNG and a 40 MB TGA of the same image become the same few megabytes once the engine imports and compresses them. Always read the size in the engine's importer or memory profiler.

    The texture inspector's preview footer shows the imported size and format for the selected platform. Window → Analysis → Memory Profiler lists textures in a captured build by size. Max Size, Format and Compression can be overridden per platform tab in the importer.

    Same importer and profiler as HDRP. On mobile targets the platform tab defaults to ASTC; check the block size there, because ASTC 4×4 is four times the memory of ASTC 8×8.

    The texture editor shows Resource Size and the format chosen by the Compression Settings. In the console, ListTextures prints every loaded texture with size and format; the Size Map on an asset shows what it pulls in. Maximum Texture Size and LOD Bias cap resolution without reimporting.

    Mipmaps and how the GPU picks one

    A mip chain stores the texture at full size, then half, quarter and so on down to 1×1. Each level has a quarter of the texels of the one before, so the whole chain adds up to a third more:

    Mips prevent : far away, one pixel covers many texels, and picking just one of them gives a different texel each frame, so detail crawls and sparkles. A smaller mip has already averaged them. They also keep neighbouring pixels reading neighbouring texels, which stay in the GPU's texture cache.

    The GPU picks the level by itself. Pixels are shaded in 2×2 (why quads matter for cost), so it can measure how much the UV changes from one pixel to the next: the ddx(uv) and ddy(uv). Turned into texels, that says how many texels one pixel spans; its log₂ is the mip level:

    With , the GPU takes several samples along the long side of the pixel's footprint and picks the mip from the short side, so floors at a grazing angle stay sharp. Compare in the lab.

    Texel density

    is texels per metre of surface. It keeps a project consistent: if a wall gets 512 px/m and the crate next to it 2048 px/m, the crate looks sharp and the wall blurry, although both "are 2K textures".

    How much density can the screen show? It depends on how many pixels a metre of surface covers, which falls with distance (the perspective divide). Compare the two, and you know which mip the GPU will pick and whether the top mips are ever seen:

    At 1080p and a 60° field of view, a surface 1 m away gets about 935 screen pixels per metre. Anything above that is invisible at that distance and only costs memory. Typical targets are 1024 px/m for first-person games, where players press against walls, and 512 px/m for third-person cameras. Pick a number per project, write it down, and check assets against it.

    Rule of thumbEach halving of distance needs double the density. A prop only ever seen from 4 m needs a quarter of the density of one the player can touch.

    Unity has no built-in density view. Use a checker texture with known texels per meter, or the mip map views in HDRP's Rendering Debugger (Rendering panel) to see where textures are under- or over-sampled.

    A checker material with a fixed tiling and a known texels-per-meter value is the quickest density check. Recent Unity 6 versions add mipmap debug views to the Rendering Debugger for URP as well.

    The Required Texture Resolution view mode compares texture resolution with what the screen needs, and Texture Streaming Accuracy modes show where the streamer guesses wrong. Both are under Optimization Viewmodes.

    Block compression

    GPU texture formats are not JPEG. The GPU must read any texel at once without decoding the rest of the image, so the texture is cut into fixed 4×4 and every block compresses to the same number of bytes. To find texel (x, y), the GPU computes the block index directly.

    The oldest scheme, (DXT1), stores a block in 8 bytes: two endpoint colours and a 2-bit index per texel. The two endpoints and two blends between them at ⅓ and ⅔ form a four-colour palette; every texel stores which of the four it is closest to. Here is the idea in one channel:

    That design explains every BC1 artefact. All four palette colours lie on one straight line through RGB space, so a block containing red, green and blue at once cannot be represented and smears. And the endpoints are stored with 5 bits for red and blue and 6 for green, so smooth gradients step. Click blocks in the lab to see both.

    In the importer's platform override choose formats directly: RGB Compressed BC1, RGBA Compressed BC7, R Compressed BC4, RG Compressed BC5, RGB HDR Compressed BC6H. With Automatic, the Compression quality setting decides; High Quality usually selects BC7.

    Same formats on desktop. For Android and iOS the default is ASTC with a block size per texture; 6×6 is a common middle ground for color, 4×4 for normals and UI, 8×8 for large blurry maps.

    Pick a Compression Settings preset rather than a raw format: Default (BC1, or BC3 with alpha), Normalmap (BC5), Masks (BC1/BC3 with sRGB off), Grayscale (single channel), HDR and HDR Compressed (BC6H), BC7. The preset also sets sRGB and mip behaviour correctly.

    Colour data and other data

    Colour textures are painted on sRGB monitors, so they are stored (what that means). When the shader samples them, the GPU decodes to linear values for free, because lighting maths must happen in linear.

    Everything else is data: roughness, metallic, AO, masks, height, normals. Those numbers mean exactly what they say and must be imported with sRGB off. If a roughness map is flagged as sRGB, the GPU "decodes" it anyway:

    Every surface becomes glossier than painted, and the artist compensates by hand until nothing matches the reference.

    Channel packing

    Roughness, metallic and AO are each a single number per texel. Storing each in its own RGB texture wastes two thirds of it and costs three samples. puts up to four greyscale maps into the R, G, B and A of one texture (a float4, read with swizzles):

    Two details decide whether a packed map looks good. The format: BC1 and BC3 encode R, G and B together along one line, so unrelated maps interfere; BC7 handles it far better, and alpha is always compressed separately, which makes A the best slot for the most important map. The layout: each engine's standard shader expects a specific one, and Unity stores smoothness where Unreal conventions store roughness. Smoothness = 1 − roughness, so moving maps between engines means inverting that channel, not just moving it.

      Normal maps

      A tangent-space stores a direction per texel in the surface's own frame (tangent space): X along U, Y along V, Z out of the surface. Directions run from −1 to 1, texels from 0 to 1, so each component is stored as n · 0.5 + 0.5. Flat is (0, 0, 1), stored as (0.5, 0.5, 1): the typical lilac.

      A normal has length 1 and Z is always positive in tangent space, so Z can be rebuilt from X and Y. Engines store only X and Y, in a two-channel format () that gives each its own high-precision block:

      The one convention that differs between tools is the sign of Y, the . OpenGL style (Y+) means green points up the texture, DirectX style (Y−) down. Unity and Blender use Y+, Unreal and 3ds Max use Y−. A map with the wrong convention lights as if every bump were a dent, but only for light from above or below, which is why it slips through review. A normal map changes lighting only; to make the surface hide parts of itself, add a height map and parallax.

      To combine two normal maps, such as folds and a tiling weave, see blending normals; to tile one without UVs, triplanar normals.

      Same as HDRP. Maps baked for Unreal need their green channel inverted before import; there is no flip checkbox in Unity's importer.

      Use the Normalmap compression preset (BC5, sRGB off). The texture editor has Flip Green Channel for maps baked in the OpenGL convention.

      Streaming and budgets

      Even compressed, textures rarely all fit in memory at full resolution. keeps only the mips the camera needs and loads finer ones as you approach, inside a fixed memory pool. It uses the same maths as the density chapter to predict the mip. Because each mip is a quarter of the one above, leaving out the top levels saves a lot:

      goes further and streams fixed-size tiles of each mip, so a huge texture costs only the tiles on screen. It suits terrain and very large unique textures, at the cost of an extra lookup per sample and occasional tile pop-in.

      A useful review habit: capture a frame in the busiest spot of a level and list the resident textures by size. The top ten usually explain most of the memory.

      Enable Texture Mipmap Streaming in Quality settings with a memory budget, and tick Mip Streaming on each texture's importer. HDRP also supports Streaming Virtual Texturing through Shader Graph's Sample Virtual Texture node.

      The same Quality setting applies. On mobile, streaming budgets are tight; combine them with lower max sizes on the Android/iOS import tabs rather than relying on streaming alone.

      Streaming is on by default with a pool set by r.Streaming.PoolSize; "Texture streaming pool over budget" warnings mean the pool is too small for what is visible. Runtime and streaming virtual textures are enabled per project and per texture (Virtual Texture Streaming).

      Build it in Unity HDRP

      Texture memory is measured, not guessed. These steps show where Unity reports it, how to turn on mip streaming with a budget, and a debug view that colours the screen by the mip level each pixel uses. Written for Unity 6 with HDRP 17; Unity 2022 LTS works the same apart from a few renamed menu entries.

      C# scriptTextureMemoryHUD.cs: streaming memory on screen.
      1. Per texture, the importer preview shows the size in memory for the selected platform and format; set formats with the import script.
      2. Enable streaming: Project Settings > Quality > Texture Mipmap Streaming (Unity 6: Mipmap Streaming), set a Memory Budget in MB, and tick Mip Streaming on large textures in the importer (the postprocessor already does).
      3. Measure: Window > Analysis > Profiler > Memory module for totals; the Memory Profiler package for a list of every texture with its size.
      4. Create the graph: in the Project window, Create > Shader Graph > HDRP > Unlit Shader Graph. Open it and check the Graph Inspector > Graph Settings.
      5. Save MipLevel.hlsl. In the graph, add a Custom Function node. Set Type to File, Source to MipLevel.hlsl and Name to MipLevel (without the _float suffix). Add the inputs UV (Vector 2), TextureSize (Float) and the outputs Mip (Float), Color (Vector 3), in that order and with those types: they must match the function's parameters. Connect Color to Base Color and put the material on objects to see which mips the camera really needs.
      6. Add TextureMemoryHUD.cs to any GameObject to see streaming memory in Play mode: current, desired (what the camera needs) and the budget.
      #ifndef ATLAS_MIP_LEVEL_INCLUDED
#define ATLAS_MIP_LEVEL_INCLUDED

// The mip level the hardware picks: log2 of the texels covered by one screen pixel.
void MipLevel_float(float2 UV, float TextureSize, out float Mip, out float3 Color)
{
    float2 dx = ddx(UV * TextureSize), dy = ddy(UV * TextureSize);
    float  d2 = max(dot(dx, dx), dot(dy, dy));
    Mip = max(0.5 * log2(max(d2, 1e-8)), 0.0);

    // mip 0 white, 1 blue, 2 green, 3 yellow, 4 orange, 5+ red
    float3 c[6] = { float3(1, 1, 1), float3(0.2, 0.45, 1), float3(0.25, 0.85, 0.35),
                    float3(1, 0.9, 0.2), float3(1, 0.55, 0.1), float3(1, 0.15, 0.1) };
    int i = min((int)Mip, 4);
    Color = lerp(c[i], c[i + 1], saturate(Mip - i));
}

#endif
