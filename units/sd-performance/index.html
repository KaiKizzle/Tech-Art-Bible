    Graph Performance

    How to keep Substance Designer graphs fast: measuring node times, why resolution dominates, greyscale and 8 bit, where exposed parameters belong in the cache, cheap versions of heavy nodes, graph structure, and what runtime rendering costs in an engine.

    Builds on Graphs, Bit Depth and Colour Space, Warps and Distortion and Pixel Processor and FX-Maps.

    Node timing

    A slow graph is usually slow because of a handful of nodes, and guessing which ones wastes an afternoon. Designer can show how long each node took. Turn on the node timing display in the Graph view toolbar: every node shows its computation time, and the slowest ones stand out. Re-measure after each change, and measure at the size you care about, since times scale with the pixel count.

    Check the engine too. Designer has a GPU engine and a CPU (SSE2) engine; Adobe calls the GPU engine much faster and recommends it unless an integrated graphics chip is not supported (switch with F9 or the engine menu). The CPU engine also lacks some formats: no 16-bit colour and no 8-bit greyscale. Adobe's guidelines note that the game-engine plugins have used the CPU engine, so a graph that feels fast in Designer can be slow when an engine renders it at runtime (rendering at runtime).

    Resolution

    Almost every node does work per pixel, so the whole graph scales with the pixel count. Each step of the parent size multiplies the time by four:

    So build at 512 or 1024, check details at 2048 now and then, and render the final size only on export. Adobe advises against switching the parent size to very high values just to export, because the whole graph, its cache and the thumbnails are recomputed; the export dialog's Batch tab overrides the output size for the export alone.

    Individual nodes can also be smaller than the graph. A Uniform Color (a flat value) needs no resolution: set it to Absolute 16 × 16 and let the next node work at the parent size. Masks and blurred inputs that are soft anyway can run one or two sizes below the parent (Relative to parent, −1 or −2) and be scaled up with a Transformation 2D. Do not go below 16 × 16, which is slower rather than faster.

    Formats and conversions

    Adobe's numbers: colour operations take about four times as long as greyscale ones, and 16 bits costs memory and bandwidth where 8 bits would do (memory per node). Three rules follow:

    • Stay greyscale until the end. Build heights, masks and roughness in L8 or L16, and create colour once, near the outputs, with a Gradient Map or a few colour Blends.
    • 16 bits only where it matters: height chains and anything a normal is computed from (banding). Masks stay 8 bit.
    • Avoid ping-pong conversions between greyscale and colour. A colour node fed into a greyscale chain converts every time; a stray colour format on a height chain (C instead of L) silently quadruples its cost.

    Caching and parameter placement

    Designer keeps every node's last result. When you change a parameter, only that node and the nodes after it are recomputed; everything before it comes from the cache. The same is true when an engine changes an exposed parameter at runtime. So where a parameter sits in the graph decides what a change costs:

    Put the parameters users will tweak often (colour tint, roughness offset, wear amount) as late in the graph as possible, ideally on nodes just before the outputs. A colour change implemented as an HSL node before the output costs one cheap node; the same change made by tinting the noise at the start costs the whole graph. Parameters that change the structure (pattern counts, seeds, tile shapes) necessarily sit early; expose fewer of them, or accept that they are slow to tweak.

    The cache costs memory. Adobe's guidelines mention a RAM limit for it, which can be raised in extreme cases; large graphs at 4k with many 16-bit colour nodes are where it runs out.

    Heavy nodes

    Adobe names blurs and warps as the most processor-intensive nodes and FX-Maps as costly. Each has a cheaper way to the same look:

    • Wide blurs: blur a downscaled copy. A blur reads a number of pixels proportional to its radius for every output pixel; at half size there are a quarter of the pixels and half the radius in pixels. For mobile, Adobe recommends downscaling transformations over blur nodes outright.
    • Warps and Slope Blur: fewer samples, fewer chained warps, and tuning at a low size (what warps cost).
    • FX-Maps and Tile Generator: fewer patterns. Adobe notes that Tile Generator gets slower with every pattern added; check the timing before and after.
    • Noises: some noises draw more patterns at a higher scale. For white noise use White Noise Fast; Fractal Sum Base and Anisotropic Noise are listed as fast options.

    Graph structure

    • Share nodes between outputs. The height, the AO and the roughness are often built from the same masks. Compute each mask once and connect it to every chain that needs it, instead of copying the nodes.
    • Switch optional features off for real. A Blend in Copy mode at opacity 0 still computes both inputs. A Blend in Switch mode skips the foreground at opacity 0 (and the background at opacity 1), so a moss layer that is off costs nothing.
    • Mind instances. Each instance of a sub-graph is computed on its own, even with the same parameters. If two places need the same result, compute it once and connect it twice.
    • Bitmaps. A Bitmap node set to Relative to parent is published at 256 × 256 in an SBSAR; keep it Absolute and resize after it. Adobe also suggests storing bitmap resources as JPEG to keep published files small.

    Runtime rendering

    An SBSAR in an engine is not a set of textures: it is the graph, and the engine plugin renders it to produce the textures, at import, when a parameter changes, or when a level loads. Everything above applies, multiplied by how many materials are rendered at once:

    For most game assets the answer is to bake: export textures, or let the plugin generate them once in the editor and ship those. Keep runtime rendering for materials that must change while the game runs (customisation, damage, seasons), render them at the smallest size that works, set the output size per platform, and spread renders over several frames or a loading screen. The implementation chapter has a queue that does that.

    Set it up in Designer and Unity HDRP

    Two tools. In Designer, a Python script that lists every node of the open graph with its type, flags the heavy kinds, and prints the base parameters it can read, so a review starts from a list instead of a hunt. In Unity, a small queue that renders runtime Substance graphs one at a time, so twenty material changes do not land in the same frame. Written for Substance 3D Designer 14 and later, Unity 6 with HDRP 17 and the Substance 3D for Unity plugin; menu names can differ slightly between versions.

    Substance DesignerNode timing, the GPU engine, a lower parent size.
    Python scriptgraph_report.py: lists heavy nodes in the open graph.
    Runtime scriptSubstanceRenderQueue.cs: spreads runtime renders over frames.
    1. In Designer, turn on node timing in the Graph view toolbar and make sure the GPU engine is active (F9 toggles it). Set the parent size to the size you ship.
    2. Open Windows > Python Editor, paste graph_report.py, open the graph you want to check and run the script. It prints each node's definition, marks blurs, warps, FX-Maps and Pixel Processors, and lists the output size and format values it can read.
    3. Work from the list and the timings together: the slowest nodes first. For each, try the cheap version from the unit (downscaled blur, fewer samples, Switch instead of Copy) and check the timing again.
    4. Move frequently tweaked exposed parameters to the end of the graph: replace an early colour tint with an HSL or Levels node right before the base colour output, driven by the same exposed input.
    5. In Unity, import the SBSAR with the Substance 3D for Unity plugin and decide per material: bake (leave runtime changes off and ship the generated textures) or runtime. Only runtime materials need the queue.
    6. Add SubstanceRenderQueue.cs to a GameObject in your bootstrap scene. Instead of calling RenderAsync() directly after setting inputs, call SubstanceRenderQueue.Request(graph). The queue renders at most one graph every few frames and drops duplicate requests.
    7. Profile on the target device with the Unity Profiler: the render calls show up on the frames where the queue submits them. Lower the plugin's output size for runtime materials until the cost fits the frame budget (frame budgets).
    # Run in Substance 3D Designer: Windows > Python Editor, with the graph to check open.
# Lists every node of the current graph, marks heavy node types, and prints the base
# parameters it can read (output size, output format). Uses only basic API calls and
# skips anything it cannot read, since property names can change between versions.
import sd
from sd.api.sdproperty import SDPropertyCategory

HEAVY = ('blur', 'warp', 'fxmap', 'pixelprocessor', 'tile_generator', 'tile_sampler', 'splatter')

def node_kind(node):
    kind = node.getDefinition().getId()
    try:                                    # instances of library graphs: show which graph
        res = node.getReferencedResource()
        if res is not None:
            kind = res.getIdentifier()
    except Exception:
        pass
    return kind

def base_values(node):
    out = {}
    for prop in node.getProperties(SDPropertyCategory.Input):
        pid = prop.getId()
        if pid in ('$outputsize', '$format'):
            try:
                out[pid] = node.getPropertyValue(prop).get()
            except Exception:
                out[pid] = '?'
    return out

graph = sd.getContext().getSDApplication().getQtForPythonUIMgr().getCurrentGraph()
if graph is None:
    print('Open a Substance graph first.')
else:
    rows = []
    for node in graph.getNodes():
        kind = node_kind(node)
        heavy = any(h in kind.lower() for h in HEAVY)
        rows.append((not heavy, kind, base_values(node)))
    rows.sort(key=lambda r: (r[0], r[1]))
    heavy_count = sum(1 for r in rows if not r[0])
    print('%d nodes, %d of a heavy kind' % (len(rows), heavy_count))
    for light, kind, vals in rows:
        flag = '   ' if light else '!! '
        print(flag + kind + ('  ' + str(vals) if vals else ''))

using Adobe.Substance.Runtime;
using UnityEngine;

// Renders runtime Substance graphs one at a time instead of all in the same frame.
// Usage: set inputs on a SubstanceRuntimeGraph, then call SubstanceRenderQueue.Request(graph).
public class SubstanceRenderQueue : MonoBehaviour
{
    [Tooltip("Frames to wait between two renders.")]
    public int framesBetweenRenders = 3;

    static SubstanceRenderQueue instance;
    readonly Queue<SubstanceRuntimeGraph> queue = new Queue<SubstanceRuntimeGraph>();
    readonly HashSet<SubstanceRuntimeGraph> pending = new HashSet<SubstanceRuntimeGraph>();
    int wait;

    void Awake()
    {
        if (instance != null && instance != this) { Destroy(gameObject); return; }
        instance = this;
        DontDestroyOnLoad(gameObject);
    }

    public static void Request(SubstanceRuntimeGraph graph)
    {
        if (instance == null || graph == null) { if (graph != null) graph.RenderAsync(); return; }
        if (instance.pending.Add(graph)) instance.queue.Enqueue(graph);   // ignore duplicate requests
    }

    void Update()
    {
        if (wait > 0) { wait--; return; }
        if (queue.Count == 0) return;
        var graph = queue.Dequeue();
        pending.Remove(graph);
        if (graph != null) graph.RenderAsync();
        wait = framesBetweenRenders;
    }
}

    The Python API is documented in Designer's scripting reference; calls such as getReferencedResource are wrapped in try so the script still runs where a call differs. The C# file uses SubstanceRuntimeGraph and RenderAsync() from Adobe's Unity scripting page; check the plugin version you install.

    The plugin supports URP as well; the queue and the advice are the same.
    In Unreal, the Substance plugin exposes graph instances to Blueprint: set inputs, then render asynchronously. Batch the renders the same way, for example from a manager actor that renders one instance per tick, and prefer baked textures for static materials.
