    Buffers and Render Targets

    Shaders only see what is already in GPU memory. This unit covers every kind of memory a shader reads and writes: meshes, per-draw values, lists of your own data, lists built on the GPU, and the images frames are drawn into.

    Builds on How a GPU Draws a Frame. Code is HLSL; engine notes show the C# and C++ side.

    A buffer is a list in GPU memory

    Shaders cannot read files or ask the CPU for data while they run. Everything they use must already sit in GPU memory. A is the simplest form of that memory: a list of equally sized elements, one after the other. Textures are the other form, a grid with filtering (Textures and Sampling).

    Two numbers describe a buffer: how many elements it holds (the count) and how many bytes each element takes (the ). Element i starts at byte i × stride, so the GPU can jump straight to any element.

    A float is 4 bytes, so a float3 is 12 and a float4 16. A particle with a position (float3), a velocity (float3) and a lifetime (float) is 28 bytes. The chapters below look at the kinds of buffers you will meet, in the order a frame uses them.

    Vertex and index buffers: the mesh

    A mesh reaches the GPU as two buffers. The vertex buffer lists every corner once, with all its data: position, normal, UV, maybe a colour. The index buffer lists triangles as three numbers each, pointing into the vertex buffer. Neighbouring triangles share corners, so they simply repeat the same index instead of storing the vertex again.

    For a flat grid of n × n quads (two triangles each), the saving is large:

    The vertex shader runs once per vertex in the vertex buffer it reads (with a cache for repeated indices), which is why the vertex count, not the triangle count, is what modelling tools and profilers usually report. Hard edges and UV seams split vertices, because one position then needs two normals or two UVs. That is why an exported mesh often has more vertices than the modelling tool showed.

    Constant buffers: values for the whole draw

    Material properties, the camera's matrices and the time are the same for every pixel of a draw. They are collected into small buffers called (cbuffers). When you call material.SetFloat, the engine writes the new value into the material's constant buffer, and the next draw reads it.

    Constant buffers have one rule that surprises everyone once: values are packed into rows of 16 bytes (four floats), and a value may not cross from one row into the next. If it would, it moves to the start of the next row and the gap stays empty. Add variables in different orders and watch the padding:

    LabPack a cbufferEach row is 16 bytes. Hatched cells are wasted padding.
    
      
    
        
    
        
    
        
    
      
    
    
    
  
    
  
    Padding wastes a little memory, but the real cost of a bad layout is bugs: if C# code fills a buffer assuming tight packing, every value after the first gap lands in the wrong place. Order constant-buffer variables from largest to smallest, or group a float3 with a float.
    
  
    Put material properties in CBUFFER_START(UnityPerMaterial). Unity lays it out for you; you only meet the 16-byte rule when you fill a cbuffer yourself from C# with SetConstantBuffer and a struct, which must then mirror the padding.
    Same as HDRP. Global values used by many shaders can go in your own cbuffer set with Shader.SetGlobalConstantBuffer, or as individual globals with Shader.SetGlobalVector.
    Material parameters become uniform buffers generated by the material compiler. In C++ shaders, BEGIN_SHADER_PARAMETER_STRUCT declares parameters and the macros insert the required alignment for you.
    
  
    


    

    
  
    Structured buffers: lists of your own data
    

  
    
    
    Sometimes a shader needs many records of its own kind: ten thousand particles, the positions of grass blades, a list of lights. A  is a list of a struct you define. Any shader can read it by index; a  can also write it.
    
    
    Compute shaders run in groups of threads, like pixel shaders run in waves, but you choose the group size and how many groups to launch. To process N elements you launch enough groups to cover them, rounding up, and the last group checks that its index is still inside the list:
    
  
    
  
    
  
    // HLSL: a compute shader that moves every particle
struct Particle { float3 pos; float3 vel; float life; };   // stride 28 bytes
RWStructuredBuffer<Particle> _Particles;
uint _Count; float _DeltaTime;

[numthreads(64, 1, 1)]
void Simulate(uint3 id : SV_DispatchThreadID)
{
    if (id.x >= _Count) return;                // the last group may run past the end
    Particle p = _Particles[id.x];
    p.pos += p.vel * _DeltaTime;
    p.life -= _DeltaTime;
    _Particles[id.x] = p;
}
    
  
    var buf = new GraphicsBuffer(GraphicsBuffer.Target.Structured, count, 28); then buf.SetData(array), compute.SetBuffer(kernel, "_Particles", buf) and compute.Dispatch(kernel, Mathf.CeilToInt(count / 64f), 1, 1). A material reads it with material.SetBuffer("_Particles", buf) and StructuredBuffer<Particle>. Call buf.Release() when done.
    Same API as HDRP. On mobile, check SystemInfo.supportsComputeShaders and the maximum number of buffers a vertex shader may read, which can be as low as zero on old GPUs.
    In the Render Dependency Graph: FRDGBufferRef Buf = GraphBuilder.CreateBuffer(FRDGBufferDesc::CreateStructuredDesc(sizeof(FParticle), Count), TEXT("Particles"));, a UAV with GraphBuilder.CreateUAV(Buf) for writing, and FComputeShaderUtils::AddPass with FComputeShaderUtils::GetGroupCount(Count, 64). Niagara exposes similar data to artists without C++.
    
  
    


    

    
  
    Append buffers: collecting a list on the GPU
    

  
    
    
    Often only some elements produce output: the grass blades that are inside the camera view, the particles that are still alive, the pixels brighter than a threshold. Thousands of threads run at once and none of them knows how many others will also produce something, so none can know in advance at which index to write.
    
    
    An  solves this with a hidden counter. Each thread that wants to add an element calls Append; the GPU increments the counter atomically (no two threads can get the same number) and writes the element at the old value. Run the lab a few times:
    
  
    
  
    
    
    LabSixteen threads, one counterThreads whose value passes the test append their ID. The order changes every run.
    
    
    
      
    
      
    
        
    
        
    
        
    
      
    
    
    
  
    
  
    
    
    Three things to remember. The order is not defined; never rely on it. The counter is not reset automatically; reset it to 0 before every dispatch or the list keeps growing. And the CPU does not know the final count, so the usual next step stays on the GPU: copy the counter into an arguments buffer and draw that many instances with an indirect draw call.
    
  
    
  
    // HLSL: keep only visible grass blades
StructuredBuffer<float3>       _AllBlades;
AppendStructuredBuffer<float3> _Visible;    // has a hidden counter

[numthreads(64, 1, 1)]
void Cull(uint3 id : SV_DispatchThreadID)
{
    if (id.x >= _Count) return;
    float3 p = _AllBlades[id.x];
    if (InsideFrustum(p))
        _Visible.Append(p);                   // counter++ and write, as one atomic step
}

// The same without an append buffer, on platforms or engines that prefer it:
RWStructuredBuffer<float3> _Out;
RWStructuredBuffer<uint>   _Counter;           // one uint, reset to 0 each frame
//   uint slot; InterlockedAdd(_Counter[0], 1, slot); _Out[slot] = p;
    
  
    visible = new GraphicsBuffer(GraphicsBuffer.Target.Append, maxCount, 12);. Each frame: visible.SetCounterValue(0), dispatch the cull kernel, then GraphicsBuffer.CopyCount(visible, args, 4) to write the count into an indirect-arguments buffer (GraphicsBuffer.Target.IndirectArguments, here at the instance-count slot) and draw with Graphics.RenderMeshIndirect or RenderPrimitivesIndirect. Reading the count back to C# with GetData stalls the CPU; avoid it every frame.
    Same API as HDRP. Some mobile drivers handle append buffers poorly; the InterlockedAdd version shown above behaves the same everywhere.
    Engine code mostly uses the InterlockedAdd pattern on an RDG buffer created with FRDGBufferDesc::CreateStructuredDesc plus a separate counter buffer, then an indirect dispatch or draw that reads the count on the GPU. Niagara GPU simulations do this for you when particles spawn and die.
    
  
    


    

    
  
    Render targets: images you draw into
    

  
    
    
    The pixel shader's output has to go somewhere. A  is a texture the GPU draws into instead of reading from. The final image is one, but a frame uses many more: depth, normals for lighting, a half-resolution buffer for bloom, a shadow map. A later pass reads them as ordinary textures, which is how a pixel finally gets to see its neighbours' results (the rule from chapter 3 of How a GPU Draws a Frame).
    
    
    Their memory is easy to work out and adds up quickly at high resolutions:
    
  
    
  
    
  
    
    
    Two kinds deserve a name. The depth buffer stores, per pixel, the distance of the nearest surface drawn so far; the depth test compares against it before shading (overdraw), and many effects read it afterwards (Reading the Depth Buffer). A G-buffer is a set of render targets written at the same time (albedo, normal, roughness…) so that lighting can run once per pixel afterwards; this is deferred rendering, the default in HDRP and Unreal.
    
  
    
  
    


    

    
  
    Build it in Unity HDRP
    
  
    Here a C# script fills a structured buffer with marker positions every frame, and a shader loops over them: the same pattern used for per-object data, wind zones, footprints in snow or interaction points on foliage. Written for Unity 6 with HDRP 17; Unity 2022 LTS works the same apart from a few renamed menu entries.
    
  
    C# scriptMarkerBuffer.cs: creates a GraphicsBuffer and binds it globally.
    HLSL fileMarkers.hlsl: reads the buffer in a Custom Function.
    Shader GraphA Lit graph that highlights the surface near any marker.
    

    1. Add MarkerBuffer.cs to an empty GameObject and drag a few objects into Markers. The script creates a GraphicsBuffer of float4 (count × 16 bytes), fills it with positions and radii, and binds it with Shader.SetGlobalBuffer.
    2. Create the graph: in the Project window, Create > Shader Graph > HDRP > Lit Shader Graph. Open it and check the Graph Inspector > Graph Settings.
    3. Add a Position node in Absolute World space (the buffer holds absolute positions).
    4. Save Markers.hlsl. In the graph, add a Custom Function node. Set Type to File, Source to Markers.hlsl and Name to Markers (without the _float suffix). Add the inputs PositionAWS (Vector 3) and the outputs Mask (Float), in that order and with those types: they must match the function's parameters. The buffer and count are declared in the file itself, so they need no node inputs.
    5. Use Mask to blend in an emissive colour. Move the marker objects: every material using the graph reacts.
    6. Release buffers when you are done (OnDisable): GPU memory is not garbage-collected.
    

    using UnityEngine;

// Uploads marker positions to the GPU every frame as a structured buffer of float4.
[ExecuteAlways]
public class MarkerBuffer : MonoBehaviour
{
    public Transform[] markers;
    public float radius = 1f;

    GraphicsBuffer buffer;
    Vector4[] data = new Vector4[1];
    static readonly int MarkersId = Shader.PropertyToID("_Markers");
    static readonly int CountId = Shader.PropertyToID("_MarkerCount");

    void Update()
    {
        int n = markers == null ? 0 : markers.Length;
        int capacity = Mathf.Max(n, 1);                       // a buffer cannot be empty
        if (buffer == null || buffer.count != capacity)
        {
            buffer?.Release();
            buffer = new GraphicsBuffer(GraphicsBuffer.Target.Structured, capacity, sizeof(float) * 4); // stride 16
            data = new Vector4[capacity];
        }
        for (int i = 0; i < n; i++)
        {
            Vector3 p = markers[i] != null ? markers[i].position : Vector3.zero;
            data[i] = new Vector4(p.x, p.y, p.z, radius);
        }
        buffer.SetData(data);
        Shader.SetGlobalBuffer(MarkersId, buffer);
        Shader.SetGlobalInt(CountId, n);
    }

    void OnDisable()
    {
        buffer?.Release();
        buffer = null;
    }
}
    #ifndef ATLAS_MARKERS_INCLUDED
#define ATLAS_MARKERS_INCLUDED

StructuredBuffer<float4> _Markers;   // xyz = absolute world position, w = radius
int _MarkerCount;

void Markers_float(float3 PositionAWS, out float Mask)
{
    Mask = 0;
    for (int i = 0; i < _MarkerCount; i++)
    {
        float4 m = _Markers[i];
        float  d = distance(PositionAWS, m.xyz);
        Mask = max(Mask, 1.0 - smoothstep(m.w * 0.7, m.w, d));
    }
}

#endif
    

    The buffer's C# struct and the HLSL type must match byte for byte: the stride you pass (16 here) is the size of one element. For data the GPU writes itself, see Compute Shaders; for an append buffer, create it with GraphicsBuffer.Target.Append, call SetCounterValue(0) each frame, and use GraphicsBuffer.CopyCount to get the count into an arguments buffer for indirect drawing.
    

    Identical; use Position in World space (URP is not camera-relative). Structured buffers need compute-capable hardware (not WebGL, not some older Android GPUs).
    Materials cannot bind arbitrary structured buffers. Use a small data texture (one texel per marker, written from Blueprint with a Render Target or a texture created in C++), a Material Parameter Collection for a handful of values, or Niagara Data Interfaces for large GPU lists.
